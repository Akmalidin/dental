# ИИ-помощник с доступом к данным клиники

Дата: 2026-09-20

## Контекст

В проекте уже есть ассистент: панель в `templates/newui/base.html` (наследуют 30 шаблонов, то есть она на всех страницах `/new/*`), распознавание речи локальным `faster-whisper`, вызов по имени через Web Speech API и свободный вопрос-ответ через YandexGPT (`apps/notifications/voice.py::ask_ai`).

Чего у него нет — **доступа к данным клиники**. Это уже проявилось на проде: сотрудники спрашивают «найди пациента …», «сколько приёмов у …», а запрос уходит в общий ИИ-чат, который о клинике ничего не знает. В коде это отмечено комментарием в `apps/notifications/views.py::voice_command`.

Вторая проблема — память разговора живёт в переменной `voiceChatHistory` в `static/newui/app.js` и теряется при каждом переходе между страницами, потому что страницы серверные, а не SPA.

## Цель

Дать ассистенту читать данные своей клиники и помнить разговор между страницами. Только чтение: никаких записей в БД и никакой отправки сообщений. Действия — следующий этап, за рамками этой спеки.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Для кого | Сотрудники клиники, в рамках своей клиники |
| Какие данные уходят в модель | Полные, включая имена и диагнозы |
| Охват вопросов | Готовые инструменты, SQL как запасной вариант |
| Размещение кода | Новое приложение `apps/assistant/` |
| Память разговора | На сервере, в БД, привязана к сотруднику |
| Провайдер | OpenAI (function calling), YandexGPT как запасной |

Передача медицинских данных внешнему обработчику за пределы ЕС — осознанное решение владельца продукта. На стороне OpenAI перед запуском включается zero data retention и оформляется DPA; в коде это не отражается.

## Границы

Не входит:

- любые действия, меняющие данные (запись, отмена, отправка сообщений)
- изменение панели ассистента и вызова по имени — они уже работают
- замена YandexGPT: он остаётся запасным провайдером
- доступ супер-админа к данным всех клиник сразу

## Архитектура

Новое приложение `apps/assistant/`, пять модулей с одной задачей каждый:

- **`provider.py`** — вызов OpenAI с function calling. Если ключ не задан или запрос не прошёл, вызывается существующий `ask_ai` (YandexGPT): ассистент продолжает отвечать на общие вопросы без доступа к данным, а не отдаёт ошибку.
- **`tools.py`** — реестр инструментов. Каждый инструмент: JSON-схема параметров для модели плюс функция, принимающая пользователя и параметры и возвращающая строки.
- **`sql.py`** — песочница для запасного SQL.
- **`models.py`** — `Conversation` и `Message`.
- **`service.py`** — оркестрация: поднять историю, вызвать провайдера, выполнить инструмент, сохранить реплики.

`apps/notifications/voice.py` остаётся про распознавание речи. `voice_command(mode=chat)` в `apps/notifications/views.py` превращается в тонкую делегацию в `service.answer()`.

## Изоляция клиник

Изоляцию обеспечивает код и база, а не доверие к модели. Модель никогда не передаёт идентификатор клиники — он берётся из текущего запроса.

**Инструменты.** Работают через обычные менеджеры (`Patient.objects`, `Appointment.objects` и т.д.), которые уже скоупятся `ClinicManager` по текущей клинике (`apps/tenancy.py`). Модель передаёт только прикладные параметры: дату, имя для поиска, период.

**Запасной SQL.** Здесь запрос пишет модель, поэтому ограничения ставятся в PostgreSQL:

- отдельная схема `ai` с вьюхами, которые фильтруют строки по `current_setting('app.clinic_id')`
- отдельная роль БД, которой выдан `SELECT` только на схему `ai` и ничего больше
- `statement_timeout` на соединении
- принудительный `LIMIT`, если его нет в запросе
- разрешён только `SELECT`

Даже корректно сформулированный запрос к чужим данным вернёт пустой результат, потому что вьюха их не отдаёт.

## Память разговора

```
Conversation
    user        FK -> users.User
    clinic      FK -> users.Clinic
    created_at, updated_at

Message
    conversation FK -> Conversation
    role         user | assistant
    text
    tool_name    пусто, если инструмент не вызывался
    tool_args    JSON
    rows_count   сколько строк вернул инструмент
    created_at
```

Одна активная беседа на сотрудника. Беседа считается активной, если последняя реплика была менее 12 часов назад; иначе следующий вопрос открывает новую. Это даёт «продолжить разговор» в течение смены и не превращает историю в одну бесконечную ленту. Кнопка «Очистить» в панели закрывает текущую беседу и открывает пустую.

В контекст модели уходят последние 12 реплик — как сейчас в клиенте.

`static/newui/app.js` перестаёт быть источником истины: `voiceChatHistory` больше не хранит разговор и не отправляется в `history`. Панель подгружает беседу с сервера при открытии — отдельным GET-эндпоинтом, возвращающим реплики активной беседы.

Поля `tool_name`, `tool_args`, `rows_count` — журнал: видно, какой инструмент отработал и сколько строк ушло наружу. Сами строки не дублируются, они есть в основных таблицах.

Срок хранения 30 дней, чистка management-командой по крону.

## Обработка отказов

| Что сломалось | Поведение |
|---|---|
| Ключ OpenAI не задан или запрос не прошёл | Падаем на YandexGPT, отвечаем без данных |
| Инструмент бросил исключение | Модели возвращается текст ошибки, она отвечает словами |
| SQL превысил таймаут или нарушил ограничения | Ответ «не смог посчитать», запрос пишется в журнал |
| Оба провайдера недоступны | Понятное сообщение пользователю, панель не ломается |

## Этапы

**Первый.** Память разговора, каркас модуля, провайдер OpenAI и 5-6 ходовых инструментов: записи на дату, поиск пациента, должники, выручка за период, загрузка врача. Закрывает известный прод-баг с «найди пациента».

**Второй.** Остальные инструменты и SQL-песочница со схемой `ai`.

**Третий.** Действия. Лягут как новый тип инструмента с проверкой прав, не затрагивая остальное. В эту спеку не входят.

## Тестирование

Главный тест — межклиниковая изоляция: сотрудник одной клиники спрашивает про пациента другой и не получает ничего. Отдельно для инструментов, отдельно для SQL-песочницы.

Остальное: каждый инструмент на своих данных; провайдер с замоканным HTTP, в OpenAI тесты не ходят; запасной путь на YandexGPT при недоступном OpenAI; сохранение и подъём истории между запросами.

## Риски

- **Стоимость.** Каждый вопрос — один-два вызова модели. Нужен потолок на клинику или на сотрудника; конкретные цифры определяются после первого этапа по факту использования.
- **Качество запасного SQL.** Модель может сгенерировать корректный, но бессмысленный запрос. Ограничения защищают данные, но не от неверного ответа — поэтому SQL именно запасной, а частые вопросы закрываются инструментами.
- **Wake-word только в Chrome.** Ограничение Web Speech API, на этот дизайн не влияет.
